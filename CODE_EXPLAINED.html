Optimal Execution Engine: reading the code

What this project does, how the folders and modules fit together, the real mathematics inside the scheduling and cost code, and the places where it is weaker than it first looks.

How to use this

The sections follow the order the code actually runs, starting from src/optimal_execution_engine/cli.py. Every code snippet is copied from the source. Every number in a Sample data box was produced by running this repository on the tracked file data/raw/sample_intraday_bars.parquet; nothing is estimated. This page explains structure and behaviour, not line-by-line syntax.

The process in plain English

The project takes 5-minute price bars for the first hour of the trading day. It watches the first six bars, up to 09:55 Eastern Time, and from them predicts how choppy the price will be over the next six bars, from 10:00 to 10:25. It then takes the square root of that prediction to turn a variance into a volatility, hands it to a trade-scheduling model, and buys 10,000 shares across the later six bars using three different schedules so their costs can be compared. The point of the repository is the discipline of the pipeline - the information cutoff, the walk-forward testing, the offline data contract - rather than the forecast itself.

Why the settings load the way they do

Environment variables beat the file. load_settings calls load_dotenv() and then, for each ClickHouse field, prefers the environment value when it is present and non-empty. This lets a password live in a local .env that is never committed while config.toml stays safe to track. Note this override applies only to the [clickhouse] block; opening_window_bars and the rest come from the file alone.

Trap

DEFAULT_SLICE_COUNT, DEFAULT_ORDER_SHARES, DEFAULT_RISK_AVERSION and the three walk-forward window sizes are constants at the top of cli.py, not settings in config.toml. Changing the order size or the risk aversion means editing Python. That is a deliberate simplification, but it means the file called config.toml does not hold every tunable number in the project.

02The data boundary

The rule is that the default run reads local files only. Three functions enforce and shape that.

validate_cache_pair — refuse data that cannot describe itself

Each dataset is a pair: sample_intraday_bars.parquet plus sample_intraday_bars.meta.json. The validator checks that both files exist, that the JSON parses, that 21 required keys are present, and then checks the values of several of them: row_count must be a non-negative integer, bar_frequency and expected_session_scope must be non-empty text, timestamp_coverage must be a dictionary carrying six named fields, intended_use must be one of three allowed words, and portable_parquet_source must be exactly True.

What it does

Input: a path to a Parquet file. Output: a CacheValidationResult carrying a true/false flag, a readable message, and both paths. Role: it is the only thing standing between a corrupt local file and a silent wrong answer downstream.

Why the description file is checked so hard

The claim the project makes is that it runs anywhere with no database. That claim rests entirely on these two files being self-describing. Checking that intended_use is one of a fixed set of words, rather than just present, is what stops a placeholder file from quietly passing as real data.

03Cutting the day in two

This is the heart of the project's claim to be honest. The day is split at bar six. What is known before the cutoff can be a predictor; what happens after it is the thing being predicted; and no return is allowed to sit in both.

time     09:30 ...                  09:55|10:00 ...              10:25

returns        r1   r2   r3   r4   r5    |  r6   r7   r8   r9  r10  r11

compute_log_returns

The formula

$$r_{d,t}=\log\!\left(\frac{P_{d,t}}{P_{d,t-1}}\right)$$

$P_{d,t}$ is the closing price of bar $t$ on day $d$, with $t$ counted from $0$ at 09:30. $r_{d,t}$ is the log return over that bar. The grouping is by symbol and day, so $r_{d,0}$ is undefined: there is no bar before the open. Using the natural logarithm makes returns add up across bars, which is what lets squared returns be summed into a variance.

compute_opening_window_realized_variance and compute_remaining_window_realized_variance

The formula

$$RV^{\text{open}}_d=\sum_{t\lt m} r_{d,t}^2 \qquad\qquad RV^{\text{remaining}}_d=\sum_{t\ge m} r_{d,t}^2$$

$m$ is opening_window_bars, which is 6. $RV^{\text{open}}_d$ is the opening realized variance and $RV^{\text{remaining}}_d$ is the target. The word "realized" means the variance is measured from returns that actually happened, not estimated from a model. Because $r_{d,0}$ is undefined, the opening sum runs over $t=1,\dots,m-1$ (five returns) after the code replaces the missing value with zero; the target sum runs over $t=m,\dots,n_d-1$ (six returns), where $n_d$ is the number of bars on day $d$. The two sets do not overlap.

The whole 55-day series of targets falls monotonically, day after day, from 4.879e-06 to about 4.5e-06. Real intraday variance does not behave like that. This is the clearest single sign that the tracked file is a constructed sample, not market history.

Why the target starts at bar six and not bar seven

The return labelled $r_{d,6}$ spans the close of bar 5 (09:55) to the close of bar 6 (10:00). Bar 5's close is known at the cutoff; bar 6's close is not. So $r_{d,6}$ is genuinely unknown at forecast time and belongs in the target. Dropping it would throw away the first sixth of the thing being predicted, and including bar 5's own return would leak. The code's comment states exactly this reasoning.

Trap

The opening calculation replaces the missing first return with zero (.fillna(0.0)) before squaring, while the target calculation does not, because it never meets a missing value. That asymmetry is correct but easy to "tidy" into a bug: adding fillna to the target would silently turn a genuinely absent return into a zero-variance contribution the day a dataset arrives with a gap in it.

Guard

Before summing, the target function counts bars per symbol and day and raises if any session has opening_window_bars or fewer. The message names every offending session, for example AAPL/2025-12-24, rather than returning an empty group that would look like a missing day later on.

04Predictors

build_opening_feature_table — three numbers from the first six bars

The formula

$$\text{opening return}_d=\log\!\left(\frac{C_{d,m-1}}{O_{d,0}}\right),\qquad \text{opening range}_d=\frac{H_d-L_d}{O_{d,0}},\qquad \text{opening log volume}_d=\log(1+V_d)$$

$O_{d,0}$ is the opening price of the first bar, $C_{d,m-1}$ the closing price of the sixth bar, $H_d$ the highest high and $L_d$ the lowest low across those six bars, and $V_d$ their total share volume. The range is divided by the opening price so it is a fraction rather than a dollar amount, which keeps it comparable across price levels. The $1+$ inside the logarithm is there so that a zero-volume window gives zero instead of negative infinity.

Check the range by hand: $(100.522899-99.91)/99.95=0.612899/99.95=0.00613205$.

Why log volume and not volume share

An earlier version of this project divided opening volume by the whole day's volume. That number cannot be computed at 09:55 because the rest of the day has not traded yet, so it leaked the future into a predictor. The code comment now says so directly: "Total-day volume is unknown at the forecast cutoff." Taking a logarithm of the opening volume alone keeps the predictor observable and compresses a five-figure share count onto a scale close to the other predictors, which helps an unregularised least-squares fit.

build_feature_table — yesterday and the recent past

def _lagged_rolling_mean(series: pd.Series, window: int) -> pd.Series:
    return series.shift(1).rolling(window=window, min_periods=window).mean()
The formula

$$\text{lag}_d=RV^{\text{remaining}}_{d-1},\qquad \text{roll}^{(w)}_d=\frac{1}{w}\sum_{j=1}^{w}RV^{\text{remaining}}_{d-j}$$

$w$ is the window length, 5 or 10 trading days. The sum runs from $j=1$, never $j=0$, so today's own target is never inside its own predictor. In code that is the .shift(1) placed before .rolling(...). Reversing those two calls would put today's value into the average and produce a model that appears to forecast almost perfectly.

05The modelling table

build_modeling_dataset_from_bars is the one call that turns bars into a table ready for fitting. It computes the target, the opening variance, and the opening predictors, joins the opening variance onto the predictors, then hands both halves to build_feature_table and selects a fixed column list.

What it does

Input: the prepared bar frame and the cutoff. Output: 45 rows by 10 columns, one row per trading day, sorted by symbol then date. Role: the only thing the modelling and evaluation code ever sees. Everything about timing has already been decided by the time this table exists.

The weakness, stated honestly

Look at the four variance columns above: they agree to three significant figures. On this tracked sample the opening variance, yesterday's target, the 5-day average and the 10-day average are all nearly the same number, and the target is a smooth continuation of them. Any linear combination can hit the target almost exactly. That is why the fit later looks impossibly good. It is a property of the sample file, not of the method.

06Three models

ModelPrediction for day $d$Why it is here
Persistence$\hat{y}_d=RV^{\text{remaining}}_{d-1}$The hardest baseline to beat for anything that behaves like volatility. If a model cannot beat "same as yesterday", it has earned nothing.
Rolling mean$\hat{y}_d=\frac{1}{5}\sum_{j=1}^{5}RV^{\text{remaining}}_{d-j}$Trades responsiveness for stability. Beats persistence when the series is noisy, loses when it trends.
Linear$\hat{y}_d=\beta_0+\sum_{k=1}^{7}\beta_k x_{d,k}$The only fitted model. Seven predictors, one intercept.

The first two are one line each: they simply read a column that build_feature_table already lagged. All the leakage protection lives in the feature code, not the model code.

fit_linear_model — least squares, written out

ones_column = np.ones((feature_matrix.shape[0], 1), dtype=float)
design_matrix = np.hstack([ones_column, feature_matrix])

# Solve min ||X beta - y||_2 using least squares for stability.
fitted_parameters, _, _, _ = np.linalg.lstsq(design_matrix, target_vector, rcond=None)
The formula

The objective, the condition that solves it, and the form the code computes:

$$\hat{\beta}=\arg\min_{\beta}\;\lVert X\beta-y\rVert_2^{2} =\arg\min_{\beta}\;\sum_{i=1}^{n}\Big(y_i-\beta_0-\sum_{k=1}^{7}\beta_k x_{i,k}\Big)^{2}$$

Setting the derivative with respect to each coefficient to zero says: the leftover errors must be uncorrelated with every predictor and must average to zero. Written out, that is the normal equations

$$X^{\top}X\,\hat{\beta}=X^{\top}y$$

which for a full-rank $X$ has the closed form

$$\hat{\beta}=(X^{\top}X)^{-1}X^{\top}y$$

$y$ is the column of 20 target values in a training window, $X$ is the 20 by 8 design matrix whose first column is all ones (the intercept) and whose other seven columns are the predictors, $n=20$ is the number of training rows, and $\hat{\beta}$ is the vector of eight fitted numbers. The code does not compute $(X^{\top}X)^{-1}$. It calls np.linalg.lstsq, which uses a singular value decomposition. That matters here: when predictors are nearly identical, as they are on this sample, $X^{\top}X$ is close to singular and inverting it directly would amplify numerical error, whereas the decomposition returns the smallest-length solution instead of blowing up.

Read these carefully: the four variance predictors receive nearly identical weights of about 0.125 each, adding to roughly 0.5. That is the classic fingerprint of collinear predictors - the decomposition has spread one effect evenly across four columns because it cannot tell them apart. The weight on log volume is 2e-11, effectively zero. The coefficients are a numerical artefact of the sample, not an economic statement.

Trap

predict_with_linear_model refuses to run if the caller passes a predictor list in a different order from the fitted one. Without that check, reordering the columns would silently pair each coefficient with the wrong predictor and still return plausible-looking numbers.

07Walk-forward testing

build_walk_forward_splits

The formula

With $L$ the training window, $K$ the test window and $s$ the step, split $j$ (counting from zero) uses

$$\text{train}_j=[\,js,\;js+L\,),\qquad \text{test}_j=[\,js+L,\;js+L+K\,)$$

and splits are produced while $js+L+K\le n$.

$n$ is the number of rows in the modelling table, here 45. The command uses $L=20$, $K=5$, $s=5$. Because the step equals the test window, the test blocks tile the data end to end with no gaps and no overlaps. Because the step is smaller than the training window, the training blocks do overlap - the window rolls forward rather than growing.

Every test row sits strictly after every training row in its own split. Row 44 is the last row, so the loop stops.

25 of the 45 modelling days receive an out-of-sample forecast. The first 20 never do: they are only ever training data.

Why a rolling window rather than an expanding one

Each fit uses exactly the 20 most recent days. An expanding window would use all history, which gives more data but assumes the relationship is stable forever. The rolling choice is the more conservative of the two and matches how a desk would refit a short-horizon model. It also keeps every split comparable, since each is fitted on the same amount of data.

evaluate_walk_forward_split and the three loss measures

The formula

For actual values $y_i$ and forecasts $h_i$ over $N$ test rows:

$$\text{MAE}=\frac{1}{N}\sum_{i=1}^{N}\lvert y_i-h_i\rvert \qquad \text{RMSE}=\sqrt{\frac{1}{N}\sum_{i=1}^{N}(y_i-h_i)^2} \qquad \text{QLIKE}=\frac{1}{N}\sum_{i=1}^{N}\left(\log h_i+\frac{y_i}{h_i}\right)$$

MAE is the mean absolute error, RMSE the root mean squared error, and QLIKE the quasi-likelihood loss. All three are lower-is-better. MAE and RMSE are in variance units, which here are around $5\times10^{-6}$, so they look tiny no matter what. QLIKE is different: it compares the ratio $y_i/h_i$ rather than the difference, so a forecast that is half the truth is penalised the same whether the truth is large or small. That is why it is the standard choice for variance forecasts, whose scale changes by orders of magnitude. The code clips $h_i$ at $10^{-12}$ before taking the logarithm, because $\log 0$ is undefined and a linear model is free to predict a negative variance.

The formula

$$\hat{\sigma}_d=\sqrt{\widehat{RV}^{\text{remaining}}_d}$$

$\widehat{RV}^{\text{remaining}}_d$ is the forecast variance for day $d$, in squared-return units, and $\hat{\sigma}_d$ is a volatility, in return units. The scheduler's input is a volatility, so the square root is not cosmetic: feeding a variance straight in would make the number roughly 400 times too small on this data and the schedule would collapse to equal slices.

Why the timing is arranged this way

run_batch_experiment only ever loops over dates that received an out-of-sample forecast. On each of those it splits the day into information_bars (0 to 5) and execution_bars (6 to 11), builds the order from the last information bar, and passes only the execution bars to the simulator. A reader auditing this project for look-ahead should check exactly these four lines, and they hold up.

The unit mismatch nobody should skip past

The field is called daily_volatility, but the number put into it is the square root of a 30-minute variance. It is a 30-minute volatility wearing a daily label. The consequence is visible in the next section: with a value of 0.00216 the urgency term becomes 0.0108, and the Almgren-Chriss schedule is then indistinguishable from equal slices. The research half of this project changes the execution half by less than one basis point. The plumbing is right; the scaling is not, and the printed comparison should be read with that in mind. Converting properly would mean multiplying by $\sqrt{390/30}$, roughly 3.6, to reach a daily figure.

calibrate_market_state — what it computes when nothing is overridden

The formula

$$\sigma_{\text{bar}}=\operatorname{sd}\!\big(r_t\big),\qquad \sigma_{\text{daily}}=\sigma_{\text{bar}}\sqrt{\frac{\text{minutes per day}}{\text{minutes per bar}}}$$

$\sigma_{\text{bar}}$ is the sample standard deviation of the bar log returns (with the usual $n-1$ divisor), minutes per day is 390 (a 6.5-hour session), and minutes per bar is inferred from the timestamps, here 5. The square root of time scaling assumes returns in different bars are independent. The ratio $390/5=78$ is the number of bars in a day; the factor is $\sqrt{78}\approx8.83$. Before the fix in section 12 this line used $\sqrt{390}$, which is only correct if each bar is one minute long.

Average daily volume

$$\text{ADV}=\frac{1}{D}\sum_{d=1}^{D}\sum_{t}V_{d,t}$$

$V_{d,t}$ is the share volume of bar $t$ on day $d$ and $D$ the number of days present in the frame. Note it is the mean of per-day totals, not the sum of everything, which is what the multi-day test in tests/calibration/ pins down. On the six execution bars of 2025-12-15 the frame holds one day, so ADV comes out as that day's partial volume, 64,023 shares. Nothing in the schedules currently reads this field, so its scale does not affect any printed number.

All three take a ParentOrder and return a small table of share counts. All three end with the same reconciliation step.

build_twap_schedule

The formula

$$x_i=\left\lfloor \frac{Q}{N}\right\rfloor \text{ for } i=1..N-1,\qquad x_N=Q-(N-1)\left\lfloor \frac{Q}{N}\right\rfloor$$

$Q$ is the order size in shares (10,000), $N$ the number of slices (6), $x_i$ the shares in slice $i$, and $\lfloor\cdot\rfloor$ rounds down. TWAP stands for time-weighted average price: trade the same amount in each equal time interval. It ignores everything about the market and is the reference every other schedule is judged against.

build_vwap_schedule

The formula

$$w_b=\frac{\bar{V}_b}{\sum_{b'}\bar{V}_{b'}},\qquad x_b=\operatorname{round}(w_b\,Q)$$

$b$ indexes an intraday bucket (here bars 6 through 11), $\bar{V}_b$ is that bucket's average volume across the days in the frame, $w_b$ its share of total volume, and $x_b$ the shares allocated to it. VWAP stands for volume-weighted average price: trade more when the market trades more, so your own footprint stays a steadier fraction of activity. The weights sum to one by construction, and the function raises if total volume is not positive.

build_almgren_chriss_schedule — the real optimisation

normalized_time = np.linspace(0.0, 1.0, slice_count + 1)

# urgency = lambda * sigma where lambda is risk aversion and sigma is daily vol.
urgency = max(order.risk_aversion * market_state.daily_volatility, MIN_URGENCY)

# x(t) = sinh(urgency * (1 - t)) / sinh(urgency)
inventory_curve = np.sinh(urgency * (1.0 - normalized_time)) / np.sinh(urgency)

inventory_shares = order.shares * inventory_curve
raw_slice_shares = -np.diff(inventory_shares)
In plain words

Trading everything at once costs a lot in market impact. Trading slowly means holding shares you have not bought yet while the price wanders away from you. This schedule balances those two, and the more volatile the stock, the faster it trades.

The formula

Step 1, the objective. Almgren and Chriss (2000) choose the path of remaining inventory $q(t)$ that minimises expected trading cost plus a penalty on the variance of that cost:

$$\min_{q(\cdot)}\;\underbrace{\eta\int_0^{T}\dot{q}(t)^2\,dt}_{\text{impact of trading fast}} \;+\;\underbrace{\lambda\,\sigma^{2}\int_0^{T}q(t)^{2}\,dt}_{\text{risk of holding on}}$$

Step 2, the condition that solves it. Setting the first variation to zero says: at every instant, the extra impact cost of speeding up must exactly equal the extra risk cost of still holding the position. Written as an equation that is $\eta\,\ddot{q}(t)=\lambda\sigma^{2}q(t)$, a differential equation whose solutions are the hyperbolic sine and cosine.

Step 3, the closed form this code implements. With the horizon rescaled to $t\in[0,1]$ and both endpoints fixed ($q(0)=Q$, $q(1)=0$):

$$q(t)=Q\,\frac{\sinh\!\big(\kappa(1-t)\big)}{\sinh(\kappa)},\qquad x_i=q\!\left(\frac{i-1}{N}\right)-q\!\left(\frac{i}{N}\right)$$

$q(t)$ is the shares still to buy at time $t$, $Q$ the order size, $N$ the number of slices, $x_i$ the shares traded in slice $i$, and $\sinh(z)=(e^{z}-e^{-z})/2$. $\eta$ is the temporary impact coefficient, $\lambda$ the risk aversion and $\sigma$ the volatility. $\kappa$ is the urgency: large $\kappa$ bends the curve so most shares are bought early, and $\kappa\to0$ straightens it into a line, which is TWAP.

What the code substitutes for $\kappa$. The textbook value is $\kappa=\sqrt{\lambda\sigma^{2}/\eta}\,T$. This code instead sets

$$\kappa=\max\!\big(\lambda\,\sigma,\;10^{-6}\big)$$

which is a stand-in, not the textbook quantity: there is no impact coefficient $\eta$ anywhere in the calibration, so the square root is dropped and $\eta$ is absorbed into the choice of $\lambda$. It preserves the qualitative behaviour - more volatility or more risk aversion means faster trading - but the units of $\lambda$ are no longer the units of a risk aversion in the original paper, and a given $\lambda$ has no interpretation transferable to another model. The floor of $10^{-6}$ exists because $\sinh(0)=0$ would divide by zero.

10The fill simulator

The formula

For slice $i$ with $q_i$ shares traded into a bar of volume $V_i$ at mid price $M_i$:

$$s_i=\frac{q_i}{V_i},\qquad I_i=a+b\,s_i,\qquad P_i=M_i\left(1+\delta\,\frac{I_i}{10{,}000}\right)$$

$$c_i=\delta\,(P_i-P^{\text{arr}})\,q_i,\qquad c^{\text{bps}}_i=\frac{c_i}{P^{\text{arr}}q_i}\times10{,}000,\qquad C^{\text{bps}}=\frac{\sum_i c_i}{\sum_i P^{\text{arr}}q_i}\times10{,}000$$

$s_i$ is the participation rate, the fraction of the bar's volume this slice represents. $I_i$ is the price concession in basis points, where a basis point is one hundredth of one percent; $a=2.0$ is a fixed cost paid on any trade and $b=25.0$ is how many extra basis points are paid for trading the entire bar's volume. $P_i$ is the price actually paid, worse than the mid price $M_i$. $\delta$ is $+1$ for a buy and $-1$ for a sell, which makes a buy fill above the mid and a sell fill below it, and makes the cost positive in both cases when the trade goes against you. $P^{\text{arr}}$ is the arrival price, the benchmark fixed at the moment the order was created. $c_i$ is the implementation shortfall in dollars - the gap between what was paid and what the benchmark would have cost - and $C^{\text{bps}}$ is the order-level cost, correctly weighted by each slice's notional value rather than averaged over slices.

Notice what dominates. Impact falls across the window, from 6.26 to 5.65 basis points, because volume rises. But the cost per slice climbs from 7.6 to 50.1 basis points, because the price drifts up and away from the arrival benchmark. On this sample, drift is roughly eight times more important than impact, which is why every schedule lands near 23.5 basis points and why the one that trades earliest wins.

Why the total is not the average of the slice figures

summarize_execution reports total_cost_bps as total dollars divided by total arrival notional, and separately reports mean_cost_bps, the plain average of the slice column, as a diagnostic. They agree here (23.733 against 23.723) only because the slices are nearly equal in size. Make the schedule genuinely uneven and the plain average would overweight the small slices and mislead. The notional-weighted figure is the one to quote.

Trap

The simulator pairs schedule row $i$ with bar row $i$ by position, using bars.head(len(schedule)). There is no timestamp join. A schedule whose rows are not in chronological order, or a bar frame that was not sorted, would be silently mismatched. It raises only when there are fewer bars than slices, never when the two are merely misaligned.

11Reporting and what the command prints

summarize_experiment_batch groups the per-day, per-schedule costs and computes the mean, median, standard deviation, 90th percentile and day count. It then adds a win rate against TWAP computed on date-matched pairs: the costs are pivoted so each date holds one column per schedule, rows with any missing value are dropped, and the win rate is the fraction of dates on which a schedule cost less than TWAP that same day.

Why the comparison is pivoted first

Comparing average costs across schedules would let a schedule win by being evaluated on easier days. Pivoting forces a like-for-like comparison on the same date before any averaging. TWAP's own win rate is set to zero by definition, since it cannot beat itself.

12Fixes applied

Four defects were found while reading and were fixed. All 49 tests pass afterwards, the command prints identical numbers, and the notebook still runs end to end.

WhereThe defectThe fixEffect
calibration/market_state.py units The bar volatility was multiplied by $\sqrt{390}$, the number of minutes in a trading day. The bars are 5 minutes long, so this treated every bar as one minute and overstated daily volatility by $\sqrt{5}\approx2.236$. The bar length is now read from the timestamps (median gap between consecutive bars, so overnight gaps cannot skew it) and the scaling is $\sqrt{390/\text{minutes per bar}}=\sqrt{78}$. When a frame carries no timestamps, it falls back to DEFAULT_BAR_DURATION_MINUTES, which mirrors execution.bar_duration_minutes in config.toml. On the 2025-12-15 execution bars the estimate drops from 0.0097095 to 0.0043422. No printed number changes, because the command always supplies the forecast override, but the function is no longer wrong for anyone who calls it directly.
research/evaluation.py alignment build_walk_forward_splits sorted a private copy of the frame and returned positions into that copy, while evaluate_walk_forward_split applied those positions to the caller's frame with .iloc. If the caller's frame were ordered differently, every split would silently read the wrong rows. The internal re-sort is gone. The function now checks that trade_date is non-decreasing and raises a clear error otherwise, so the positions it returns unambiguously index the frame it was given. No behaviour change on any current caller, all of which pass a date-sorted frame. A silent wrong answer became a loud failure.
cli.py robustness The single-order section asked for DEFAULT_SLICE_COUNT slices unconditionally, while the cross-day path clamped it to the number of available bars. A day with fewer than six post-cutoff bars would crash inside the simulator. The single-order path now clamps the same way: min(DEFAULT_SLICE_COUNT, len(execution_bars)). None on the tracked data, which always has exactly six. It removes a crash waiting on a short session or a larger opening_window_bars.
scripts/build_offline_research_pipeline.py index The notebook's coverage table read first_last["max"].iloc[0] for the column named last_timestamp_utc. Since the rows are grouped by date in ascending order, that is the last bar of the first day, not of the dataset. Changed to .iloc[-1], and the notebook was regenerated through the builder so the tracked notebook matches. The coverage table now reports 2026-01-16 15:25:00 rather than 2025-11-03 15:25:00, which agrees with timestamp_bounds in the metadata sidecar.

Two further weaknesses were found and deliberately not changed, because neither can be tested from here and both are in the optional database path: the extraction query in data/clickhouse.py is assembled by string formatting rather than bound parameters, and ClickHouseMarketDataClient never closes its connection. 16Limitations, stated honestly

The sample data is constructed, not observed

Prices trace a smooth curve within each day and the daily target variance falls monotonically across all 55 days. Volume is symmetric around the middle of the window. No real stock does this. Every performance number on this page describes the fixture, not a market.

The forecast does not really reach execution

Because a 30-minute volatility is being passed into a field expecting a daily one, urgency lands around 0.011 and the Almgren-Chriss schedule is equal slices to within two shares. The research half of the project currently moves the execution half by about 0.016 basis points. The wiring is correct and the scaling is not.

The impact model has no memory and no depth

Cost is a straight line in participation rate, $2.0+25.0\,s_i$ basis points, with no permanent impact, no spread crossing beyond that fixed 2 basis points, no queue position, no order book and no feedback from the trading onto later prices. Both coefficients are constants in simulator/execution.py rather than settings, and neither was estimated from anything.

The VWAP benchmark sees the future

Its weights come from the volumes of the very bars it trades into. It is a ceiling on what a perfect volume forecast could achieve, not a schedule anyone could run.

One symbol, one hour, no cross-sectional structure

The command runs AAPL alone. The other two tracked files exist but no code path compares them. There is no portfolio, no correlation between names, no risk model, and no notion that trading one stock might move another.

Twenty-five evaluation days is not a sample

Five walk-forward splits over 25 forecast days on one instrument cannot separate skill from luck. The 100 percent win rate against TWAP is 25 near-identical days pointing the same way, and the margin is 0.0155 basis points.

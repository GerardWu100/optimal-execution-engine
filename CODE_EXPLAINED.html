Optimal Execution Engine: reading the code

A concise guide to the project: its folder structure, scheduling and cost maths, and the limits of the results.

How to use this

The sections follow the code's execution order, starting at src/optimal_execution_engine/cli.py. Snippets come from the source. Numbers in Sample data boxes come from running the repository on data/raw/sample_intraday_bars.parquet; none are estimates. The page explains structure and behaviour, not every line of syntax.

The process in plain English

The project uses 5-minute price bars from the first hour of the trading day. It observes the first six bars, through 09:55 Eastern Time, and predicts price variation over the next six bars, from 10:00 to 10:25. It takes the square root of that variance forecast to get volatility, passes it to a trade-scheduling model, and buys 10,000 shares across the later six bars with three schedules. The main subject is the pipeline: its information cutoff, walk-forward testing, and offline data contract.

Why the settings load the way they do

Environment variables override the file. load_settings calls load_dotenv() and uses a present, non-empty environment value for each ClickHouse field. A password can therefore stay in an uncommitted local .env, while config.toml remains safe to track. This applies only to the [clickhouse] block; opening_window_bars and the other settings come from the file.

Trap

DEFAULT_SLICE_COUNT, DEFAULT_ORDER_SHARES, DEFAULT_RISK_AVERSION, and the three walk-forward window sizes are constants at the top of cli.py, not settings in config.toml. Changing order size or risk aversion requires a Python edit. This is simple, but config.toml does not contain every tunable number.

02The data boundary

The default run reads local files only. Three functions enforce that rule and prepare the data.

validate_cache_pair — refuse data that cannot describe itself

Each dataset has two files: sample_intraday_bars.parquet and sample_intraday_bars.meta.json. The validator checks that both exist, that the JavaScript Object Notation (JSON) parses, and that 21 required keys are present. It then checks several values: row_count must be a non-negative integer; bar_frequency and expected_session_scope must contain text; timestamp_coverage must be a dictionary with six named fields; intended_use must be one of three allowed words; and portable_parquet_source must be exactly True.

What it does

Input: a path to a Parquet file. Output: a CacheValidationResult with a true/false flag, a readable message, and both paths. Role: it blocks corrupt local data before it can produce a silent downstream error.

Why the description file is checked so hard

The project claims to run without a database. That depends on these files describing themselves. Requiring intended_use to be one of a fixed set of words, rather than merely present, prevents a placeholder file from passing as real data.

03Cutting the day in two

The day is split at bar six. Data known before the cutoff can be a predictor; later data is the target. No return belongs to both groups.

compute_log_returns

The formula

$$r_{d,t}=\log\!\left(\frac{P_{d,t}}{P_{d,t-1}}\right)$$

$P_{d,t}$ is the closing price of bar $t$ on day $d$, with $t$ starting at $0$ at 09:30. $r_{d,t}$ is that bar's log return. The calculation groups by symbol and day, so $r_{d,0}$ is undefined because no earlier bar exists. Natural-log returns add across bars, which lets the code sum squared returns into a variance.

compute_opening_window_realized_variance and compute_remaining_window_realized_variance

The formula

$$RV^{\text{open}}_d=\sum_{t\lt m} r_{d,t}^2 \qquad\qquad RV^{\text{remaining}}_d=\sum_{t\ge m} r_{d,t}^2$$

$m$ is opening_window_bars, which is 6. $RV^{\text{open}}_d$ is opening realized variance; $RV^{\text{remaining}}_d$ is the target. "Realized" means measured from actual returns, not estimated by a model. Because $r_{d,0}$ is undefined, the opening sum uses $t=1,\dots,m-1$ (five returns) after the code replaces the missing value with zero. The target uses $t=m,\dots,n_d-1$ (six returns), where $n_d$ is the number of bars on day $d$. The sets do not overlap.

The target falls every day across the 55-day series, from 4.879e-06 to about 4.5e-06. Real intraday variance does not behave this way. This is the clearest sign that the tracked file is a constructed sample, not market history.

Why the target starts at bar six and not bar seven

The return $r_{d,6}$ runs from the close of bar 5 (09:55) to the close of bar 6 (10:00). Bar 5's close is known at the cutoff; bar 6's is not. So $r_{d,6}$ is unknown at forecast time and belongs in the target. Dropping it would omit the first sixth of the target. Including bar 5's return would use information from before the cutoff as a target.

Trap

The opening calculation replaces the missing first return with zero (.fillna(0.0)) before squaring. The target calculation does not because it never encounters a missing value. Adding fillna there would turn an absent return into a zero-variance contribution when a dataset contains a gap.

Guard

Before summing, the target function counts bars per symbol and day. It raises if any session has opening_window_bars or fewer. The message names each offending session, such as AAPL/2025-12-24, instead of returning an empty group that could look like a missing day later.

04Predictors

build_opening_feature_table — three numbers from the first six bars

The formula

$$\text{opening return}_d=\log\!\left(\frac{C_{d,m-1}}{O_{d,0}}\right),\qquad \text{opening range}_d=\frac{H_d-L_d}{O_{d,0}},\qquad \text{opening log volume}_d=\log(1+V_d)$$

$O_{d,0}$ is the first bar's opening price, $C_{d,m-1}$ the sixth bar's closing price, $H_d$ the highest high, $L_d$ the lowest low, and $V_d$ the total share volume across the six bars. Dividing the range by the opening price makes it a fraction rather than a dollar amount, so it remains comparable across price levels. The $1+$ makes a zero-volume window return zero instead of negative infinity.

Sample data

highest high H = 100.522899
lowest low   L = 99.91
total volume V = 60,399 shares
out — three predictors 
opening_return      0.00491933

opening_log_volume 11.00874438

Check the range by hand: $(100.522899-99.91)/99.95=0.612899/99.95=0.00613205$.

Why log volume and not volume share

An earlier version divided opening volume by the whole day's volume. That value is unavailable at 09:55 because the rest of the day has not traded, so it leaked future information into a predictor. The code comment states: "Total-day volume is unknown at the forecast cutoff." The log of opening volume is observable and puts the five-figure share count closer to the other predictors, which helps an unregularised least-squares fit.

The formula

$$\text{lag}_d=RV^{\text{remaining}}_{d-1},\qquad \text{roll}^{(w)}_d=\frac{1}{w}\sum_{j=1}^{w}RV^{\text{remaining}}_{d-j}$$

$w$ is the window length, 5 or 10 trading days. The sum starts at $j=1$, not $j=0$, so today's target is excluded. In code, .shift(1) comes before .rolling(...). Reversing them would include today's value and make the model appear almost perfect.

05The modelling table

build_modeling_dataset_from_bars turns bars into the fitting table. It computes the target, opening variance, and opening predictors; joins the variance to the predictors; passes the result to build_feature_table; and selects fixed columns.

What it does

Input: the prepared bar frame and the cutoff. Output: 45 rows by 10 columns, one row per trading day, sorted by symbol then date. Role: the only input seen by the modelling and evaluation code. Timing is fixed before this table exists.

The weakness, stated honestly

The four variance columns agree to three significant figures. In this sample, opening variance, yesterday's target, the 5-day average, and the 10-day average are nearly identical, and the target continues their smooth pattern. A linear combination can therefore match the target almost exactly. The later fit reflects the sample file, not the method.

06Three models

ModelPrediction for day $d$Why it is here
Persistence$\hat{y}_d=RV^{\text{remaining}}_{d-1}$The hardest baseline to beat for anything that behaves like volatility. If a model cannot beat "same as yesterday", it has earned nothing.
Rolling mean$\hat{y}_d=\frac{1}{5}\sum_{j=1}^{5}RV^{\text{remaining}}_{d-j}$Trades responsiveness for stability. Beats persistence when the series is noisy, loses when it trends.
Linear$\hat{y}_d=\beta_0+\sum_{k=1}^{7}\beta_k x_{d,k}$The only fitted model. Seven predictors, one intercept.

The first two models each read a column already lagged by build_feature_table. The leakage protection is in the feature code, not the model code.

fit_linear_model — least squares, written out

ones_column = np.ones((feature_matrix.shape[0], 1), dtype=float)
design_matrix = np.hstack([ones_column, feature_matrix])

# Solve min ||X beta - y||_2 using least squares for stability.
fitted_parameters, _, _, _ = np.linalg.lstsq(design_matrix, target_vector, rcond=None)
The formula

The objective, the condition that solves it, and the form the code computes:

$$\hat{\beta}=\arg\min_{\beta}\;\lVert X\beta-y\rVert_2^{2} =\arg\min_{\beta}\;\sum_{i=1}^{n}\Big(y_i-\beta_0-\sum_{k=1}^{7}\beta_k x_{i,k}\Big)^{2}$$

Setting the derivative with respect to each coefficient to zero says: the leftover errors must be uncorrelated with every predictor and must average to zero. Written out, that is the normal equations

$$X^{\top}X\,\hat{\beta}=X^{\top}y$$

which for a full-rank $X$ has the closed form

$$\hat{\beta}=(X^{\top}X)^{-1}X^{\top}y$$

$y$ is the column of 20 target values in a training window. $X$ is the 20 by 8 design matrix: its first column is all ones (the intercept), followed by the seven predictors. $n=20$ is the number of training rows, and $\hat{\beta}$ contains eight fitted values. The code does not compute $(X^{\top}X)^{-1}$. It calls np.linalg.lstsq, which uses a singular value decomposition. That matters here because nearly identical predictors make $X^{\top}X$ close to singular. Direct inversion would amplify numerical error; the decomposition returns the smallest-length solution.

The four variance predictors each receive a weight of about 0.125, adding to roughly 0.5. These coefficients describe the sample's numerical structure, not an economic relationship.

Trap

predict_with_linear_model refuses a predictor list in a different order from the fitted list. Without this check, the coefficients would pair with the wrong predictors and still produce plausible-looking numbers.

07Walk-forward testing

build_walk_forward_splits

The formula

With $L$ the training window, $K$ the test window and $s$ the step, split $j$ (counting from zero) uses

$$\text{train}_j=[\,js,\;js+L\,),\qquad \text{test}_j=[\,js+L,\;js+L+K\,)$$

and splits are produced while $js+L+K\le n$.

$n$ is the number of rows in the modelling table, here 45. The command uses $L=20$, $K=5$, and $s=5$. Because the step equals the test window, test blocks cover the data with no gaps or overlaps. Because the step is smaller than the training window, training blocks overlap as the window rolls forward.

Sample data

Every test row sits strictly after every training row in its own split. Row 44 is the last row, so the loop stops.

25 of the 45 modelling days receive an out-of-sample forecast. The first 20 are training data only.

Why a rolling window rather than an expanding one

Each fit uses the 20 most recent days. An expanding window would use all history, giving more data but assuming the relationship stays stable. The rolling window is more conservative and matches a short-horizon refit. It also keeps every split the same size.

evaluate_walk_forward_split and the three loss measures

The formula

For actual values $y_i$ and forecasts $h_i$ over $N$ test rows:

$$\text{MAE}=\frac{1}{N}\sum_{i=1}^{N}\lvert y_i-h_i\rvert \qquad \text{RMSE}=\sqrt{\frac{1}{N}\sum_{i=1}^{N}(y_i-h_i)^2} \qquad \text{QLIKE}=\frac{1}{N}\sum_{i=1}^{N}\left(\log h_i+\frac{y_i}{h_i}\right)$$

MAE is the mean absolute error, RMSE the root mean squared error, and QLIKE the quasi-likelihood loss. All three are lower-is-better. MAE and RMSE are in variance units, which here are around $5\times10^{-6}$, so they look tiny no matter what. QLIKE is different: it compares the ratio $y_i/h_i$ rather than the difference, so a forecast that is half the truth is penalised the same whether the truth is large or small. That is why it is the standard choice for variance forecasts, whose scale changes by orders of magnitude. The code clips $h_i$ at $10^{-12}$ before taking the logarithm, because $\log 0$ is undefined and a linear model is free to predict a negative variance.

Across all five splits, MAE is 7.03e-09 for persistence, 2.12e-08 for the rolling mean, and 2.44e-14 for the linear model. The six-order improvement is a warning sign, not evidence of forecasting skill.

The weakness, stated honestly

A linear MAE of 2.4e-14 is close to double-precision rounding error. Here, the target is almost an exact linear function of the predictors, so the test measures the split protocol rather than forecasting skill. Treat the number as evidence that the pipeline is connected correctly, and nothing more.

08The bridge

predicted_variance = float(forecast_variance_by_trade_date[trade_date])

The formula

$$\hat{\sigma}_d=\sqrt{\widehat{RV}^{\text{remaining}}_d}$$

$\widehat{RV}^{\text{remaining}}_d$ is the forecast variance for day $d$, in squared-return units. $\hat{\sigma}_d$ is volatility, in return units. The scheduler needs volatility, so the square root matters: passing variance directly would make the number roughly 400 times too small on this data and collapse the schedule to equal slices.

Why the timing is arranged this way

run_batch_experiment loops only over dates with an out-of-sample forecast. For each date it splits the day into information_bars (0 to 5) and execution_bars (6 to 11), builds the order from the last information bar, and sends only the execution bars to the simulator. These are the four lines to check for look-ahead.

The unit mismatch nobody should skip past

The field is called daily_volatility, but it receives the square root of a 30-minute variance. It is 30-minute volatility with a daily label. With a value of 0.00216, urgency becomes 0.0108, so the Almgren-Chriss schedule is nearly equal slices. The research half changes the execution half by less than one basis point. The connection is right; the scaling is not. A proper daily conversion would multiply by $\sqrt{390/30}$, roughly 3.6.

calibrate_market_state — what it computes when nothing is overridden

The formula

$$\sigma_{\text{bar}}=\operatorname{sd}\!\big(r_t\big),\qquad \sigma_{\text{daily}}=\sigma_{\text{bar}}\sqrt{\frac{\text{minutes per day}}{\text{minutes per bar}}}$$

$\sigma_{\text{bar}}$ is the sample standard deviation of bar log returns, using the usual $n-1$ divisor. Minutes per day is 390 (a 6.5-hour session), and minutes per bar comes from the timestamps, here 5. Time scaling assumes returns in different bars are independent. The ratio $390/5=78$ is the number of bars in a day, giving $\sqrt{78}\approx8.83$. Before the fix in section 12 this line used $\sqrt{390}$, which is correct only for one-minute bars.

Average daily volume

$$\text{ADV}=\frac{1}{D}\sum_{d=1}^{D}\sum_{t}V_{d,t}$$

$V_{d,t}$ is the share volume of bar $t$ on day $d$, and $D$ is the number of days in the frame. ADV is the mean of daily totals, not the total across all days; the multi-day test in tests/calibration/ checks this. The six execution bars on 2025-12-15 cover one day, so ADV is that day's partial volume, 64,023 shares. The schedules do not read this field, so its scale does not affect printed numbers.

09Three schedules

Each schedule takes a ParentOrder and returns a small table of share counts. Each ends with the same reconciliation step.

build_twap_schedule

The formula

$$x_i=\left\lfloor \frac{Q}{N}\right\rfloor \text{ for } i=1..N-1,\qquad x_N=Q-(N-1)\left\lfloor \frac{Q}{N}\right\rfloor$$

$Q$ is the order size in shares (10,000), $N$ the number of slices (6), and $x_i$ the shares in slice $i$. $\lfloor\cdot\rfloor$ rounds down. TWAP means time-weighted average price: trade the same amount in each equal time interval. It ignores market conditions and is the reference for the other schedules.

build_vwap_schedule

The formula

$$w_b=\frac{\bar{V}_b}{\sum_{b'}\bar{V}_{b'}},\qquad x_b=\operatorname{round}(w_b\,Q)$$

$b$ indexes an intraday bucket (here bars 6 through 11). $\bar{V}_b$ is that bucket's average volume across the days in the frame, $w_b$ its share of total volume, and $x_b$ the shares allocated to it. VWAP means volume-weighted average price: trade more when the market trades more, so your share of activity stays steadier. The weights sum to one, and the function raises if total volume is not positive.

build_almgren_chriss_schedule — the real optimisation

normalized_time = np.linspace(0.0, 1.0, slice_count + 1)

# urgency = lambda * sigma where lambda is risk aversion and sigma is daily vol.
urgency = max(order.risk_aversion * market_state.daily_volatility, MIN_URGENCY)

# x(t) = sinh(urgency * (1 - t)) / sinh(urgency)
inventory_curve = np.sinh(urgency * (1.0 - normalized_time)) / np.sinh(urgency)

inventory_shares = order.shares * inventory_curve
raw_slice_shares = -np.diff(inventory_shares)
In plain words

Trading everything at once creates market impact. Trading slowly leaves the order exposed to price movement. This schedule balances those costs: higher volatility makes it trade faster.

The formula

Step 1, the objective. Almgren and Chriss (2000) choose the path of remaining inventory $q(t)$ that minimises expected trading cost plus a penalty on the variance of that cost:

$$\min_{q(\cdot)}\;\underbrace{\eta\int_0^{T}\dot{q}(t)^2\,dt}_{\text{impact of trading fast}} \;+\;\underbrace{\lambda\,\sigma^{2}\int_0^{T}q(t)^{2}\,dt}_{\text{risk of holding on}}$$

Step 2, the condition that solves it. Setting the first variation to zero says: at every instant, the extra impact cost of speeding up must exactly equal the extra risk cost of still holding the position. Written as an equation that is $\eta\,\ddot{q}(t)=\lambda\sigma^{2}q(t)$, a differential equation whose solutions are the hyperbolic sine and cosine.

Step 3, the closed form this code implements. With the horizon rescaled to $t\in[0,1]$ and both endpoints fixed ($q(0)=Q$, $q(1)=0$):

$$q(t)=Q\,\frac{\sinh\!\big(\kappa(1-t)\big)}{\sinh(\kappa)},\qquad x_i=q\!\left(\frac{i-1}{N}\right)-q\!\left(\frac{i}{N}\right)$$

$q(t)$ is the shares still to buy at time $t$, $Q$ the order size, $N$ the number of slices, and $x_i$ the shares traded in slice $i$. Also, $\sinh(z)=(e^{z}-e^{-z})/2$. $\eta$ is the temporary impact coefficient, $\lambda$ is risk aversion, and $\sigma$ is volatility. $\kappa$ is urgency: a large $\kappa$ value buys most shares early; $\kappa\to0$ makes the curve a line, which is TWAP.

What the code substitutes for $\kappa$. The textbook value is $\kappa=\sqrt{\lambda\sigma^{2}/\eta}\,T$. This code instead sets

$$\kappa=\max\!\big(\lambda\,\sigma,\;10^{-6}\big)$$

This is a stand-in, not the textbook quantity. Calibration has no impact coefficient $\eta$, so the square root is dropped and $\eta$ is absorbed into $\lambda$. The direction remains: more volatility or risk aversion means faster trading. But $\lambda$ no longer has the original model's units; a given $\lambda$ has no transferable interpretation. The $10^{-6}$ floor prevents division by zero because $\sinh(0)=0$.

10The fill simulator

The formula

For slice $i$ with $q_i$ shares traded into a bar of volume $V_i$ at mid price $M_i$:

$$s_i=\frac{q_i}{V_i},\qquad I_i=a+b\,s_i,\qquad P_i=M_i\left(1+\delta\,\frac{I_i}{10{,}000}\right)$$

$$c_i=\delta\,(P_i-P^{\text{arr}})\,q_i,\qquad c^{\text{bps}}_i=\frac{c_i}{P^{\text{arr}}q_i}\times10{,}000,\qquad C^{\text{bps}}=\frac{\sum_i c_i}{\sum_i P^{\text{arr}}q_i}\times10{,}000$$

$s_i$ is the participation rate: this slice's share of bar volume. $I_i$ is the price concession in basis points, where one basis point is one hundredth of one percent. $a=2.0$ is the fixed cost for any trade, and $b=25.0$ is the extra cost for trading the entire bar's volume. $P_i$ is the paid price, worse than the mid price $M_i$. $\delta$ is $+1$ for a buy and $-1$ for a sell, so costs are positive when the trade moves against you. $P^{\text{arr}}$ is the arrival price, fixed when the order is created. $c_i$ is implementation shortfall in dollars: the difference between the paid price and the benchmark cost. $C^{\text{bps}}$ is the order-level cost, weighted by slice notional rather than averaged across slices.

Impact falls from 6.26 to 5.65 basis points as volume rises. But slice cost rises from 7.6 to 50.1 basis points because price moves away from the arrival benchmark. On this sample, drift is roughly eight times more important than impact. That is why schedules cost about 23.5 basis points and earlier trading wins.

Why the total is not the average of the slice figures

summarize_execution calculates total_cost_bps as total dollars divided by total arrival notional. It also reports mean_cost_bps, the plain average of the slice costs, as a diagnostic. They agree here (23.733 versus 23.723) because slices are nearly equal. With an uneven schedule, the plain average would over-weight small slices. Quote the notional-weighted figure.

Trap

The simulator pairs schedule row $i$ with bar row $i$ by position, using bars.head(len(schedule)). It does not join timestamps. An unsorted schedule or bar frame would therefore be silently mismatched. It raises only when there are fewer bars than slices, not when rows are misaligned.

11Reporting and what the command prints

summarize_experiment_batch groups costs by day and schedule, then computes the mean, median, standard deviation, 90th percentile, and day count. It also calculates a win rate against TWAP using matching dates: each date becomes a row with one column per schedule, incomplete rows are dropped, and the win rate is the fraction of dates where a schedule costs less than TWAP.

Why the comparison is pivoted first

Comparing average costs could let a schedule win by being tested on easier days. Matching dates keeps the comparison like-for-like before averaging. TWAP's win rate is zero because it cannot beat itself.

12Fixes applied

Four defects were found and fixed. All 49 tests pass, the command prints the same numbers, and the notebook still runs end to end.

WhereThe defectThe fixEffect
calibration/market_state.py units The bar volatility was multiplied by $\sqrt{390}$, the number of minutes in a trading day. Because bars are 5 minutes long, this treated each bar as one minute and overstated daily volatility by $\sqrt{5}\approx2.236$. The bar length now comes from the timestamps (the median gap between consecutive bars, so overnight gaps cannot skew it), and scaling is $\sqrt{390/\text{minutes per bar}}=\sqrt{78}$. Without timestamps, it falls back to DEFAULT_BAR_DURATION_MINUTES, which matches execution.bar_duration_minutes in config.toml. On the 2025-12-15 execution bars, the estimate drops from 0.0097095 to 0.0043422. Printed numbers do not change because the command supplies the forecast override, but direct calls now use the right calculation.
research/evaluation.py alignment build_walk_forward_splits sorted a private copy and returned positions into it, while evaluate_walk_forward_split applied those positions to the caller's frame with .iloc. A differently ordered caller frame would make every split read the wrong rows. The internal re-sort is gone. The function now checks that trade_date is non-decreasing and raises a clear error otherwise, so its positions always index the supplied frame. Current callers pass date-sorted frames, so their behaviour is unchanged. A silent wrong answer now becomes a clear failure.
cli.py robustness The single-order section always requested DEFAULT_SLICE_COUNT slices, while the cross-day path limited the count to available bars. A day with fewer than six post-cutoff bars would crash in the simulator. The single-order path now clamps the same way: min(DEFAULT_SLICE_COUNT, len(execution_bars)). Nothing changes on the tracked data, which always has exactly six. Short sessions and larger opening_window_bars values no longer trigger this crash.
scripts/build_offline_research_pipeline.py index The notebook's coverage table read first_last["max"].iloc[0] for last_timestamp_utc. Because rows are grouped by date in ascending order, that is the last bar of the first day, not the dataset. Changed to .iloc[-1], then regenerated the notebook through the builder so the tracked notebook matches. The coverage table now reports 2026-01-16 15:25:00 rather than 2025-11-03 15:25:00, matching timestamp_bounds in the metadata sidecar.

Two further weaknesses were found but deliberately not changed because neither can be tested here and both are in the optional database path: the extraction query in data/clickhouse.py uses string formatting instead of bound parameters, and ClickHouseMarketDataClient never closes its connection. They remain in the traps section rather than being patched without tests.

16Limitations, stated honestly

The sample data is constructed, not observed

Prices follow a smooth curve each day, target variance falls across all 55 days, and volume is symmetric around the window's midpoint. No real stock behaves this way. Every performance number here describes the fixture, not a market.

The forecast does not really reach execution

A 30-minute volatility is passed to a field expecting daily volatility. Urgency is therefore around 0.011, and the Almgren-Chriss schedule differs from equal slices by at most two shares. The research half changes execution by about 0.016 basis points. The connection is correct; the scaling is not.

The impact model has no memory and no depth

Cost is a straight line in participation rate, $2.0+25.0\,s_i$ basis points. It has no permanent impact, spread crossing beyond the fixed 2 basis points, queue position, order book, or feedback from trading to later prices. Both coefficients are constants in simulator/execution.py, and neither was estimated from data.

The VWAP benchmark sees the future

Its weights come from the volumes of the bars it trades into. It shows what a perfect volume forecast could achieve, not a schedule available in real time.

One symbol, one hour, no cross-sectional structure

The command runs AAPL alone. The other two tracked files exist, but no code path compares them. There is no portfolio, cross-name correlation, risk model, or relationship between trading one stock and another.

Twenty-five evaluation days is not a sample

Five walk-forward splits over 25 forecast days on one instrument cannot separate skill from luck. The 100 percent win rate against TWAP comes from 25 near-identical days, and the margin is 0.0155 basis points.
